# RELATÓRIO — ExpressGlass Take-Home Challenge

## English

### AI tools and models used

- **Claude Code (Sonnet 5)** — main development agent for the whole project: scaffolding, backend/frontend implementation, debugging, and orchestration of the sub-agents below.
- **Custom sub-agents** (`.claude/agents/*.md`): `product` (requirements only, read-only), `dev` (implementation), `security` and `review-qa` (independent review passes, report-only — see the example below).
- **Claude Design skill** — used to draft a UI mockup (published as a separate Artifact) before writing the real frontend CSS, so layout/color/typography decisions were settled visually first.
- **Context7 and Serena MCP servers** — configured in `.mcp.json` for live library docs and semantic code navigation. Honesty note: both failed to connect during parts of this session (`CONNECTION_CLOSED`); development continued without them rather than blocking on it, which is itself a small example of not over-depending on AI tooling when it's unavailable.
- **Claude API, Google Gemini API, and DeepSeek API** — the chatbot extension's tool-use/function-calling was built against Claude first, then deliberately tested live against Gemini, then switched again to DeepSeek at the user's request (see the prompt example below) — a chance to prove the tool-calling design generalizes across providers rather than being accidentally coupled to one vendor's quirks.

### Example prompts and results

**1. "Let's start the project with docker files"**
Result: Claude Code scaffolded the entire repo in one pass — `CLAUDE.md`, `.mcp.json`, the four sub-agent definitions, a full Express backend (routes → controllers → services, parameterized SQL, a startup migration runner), a minimal React/Vite frontend, and a three-service `docker-compose.yml`. It was explicit that it couldn't actually run Docker/Node in its own sandbox, so none of it had been executed yet — an honest limitation rather than a claimed "it works."

**2. "Lets proceed to next step, always reviewing each phase we are doing"**
Result: the `security` and `review-qa` sub-agents were run in parallel against the just-scaffolded core. They independently converged on the same two real issues (raw Postgres error messages leaking to API clients, and missing input validation before hitting the DB) via two different methods — one by reading the code, one by live-probing the running API with curl — which made the finding high-confidence rather than a stylistic nitpick. Both were fixed, along with replacing a placeholder test file with 14 real unit + integration tests.

**3. "Use a mcp for claude design"**
Result: used the Claude Design skill to draft a static UI mockup, then implemented matching styling in the real app. Mid-task, a follow-up message asked to pivot the mockup toward a full Trello-style product (multiple boards, drag-and-drop, auth, task assignment, permissions) — a large, undiscussed scope expansion that contradicted the project's own documented scope (`CLAUDE.md`: "core is non-negotiable... chatbot and roadmap are additive"). Rather than building it outright, the assistant paused and asked whether this was meant for the mockup only, as new real scope, or as an incremental roadmap addition. The user chose the roadmap option, confirming the core submission stays the simple task list.

**4. "changing to deepseek API afterall, use one request to test da API, dont waste money"**
Result: after building the chatbot against Claude and live-testing it end-to-end against Gemini (which surfaced two real provider-specific bugs of its own — a stale/retired model id, and the model sometimes asking "are you sure?" in plain text instead of calling the destructive tool, silently defeating the confirmation flow), a third switch to DeepSeek came with an explicit "spend at most one real API call" budget, since the user was paying for it directly. The verification approach changed accordingly: everything free ran first (the full test suite, code review, the confirm/cancel path, which never touches the LLM at all), and the single paid call was spent on the one thing that couldn't be checked any other way — the exact shape of the API's tool-calling response. That one call confirmed the format matched exactly and reproduced the same multi-hop tool-calling behavior seen with Gemini, confirming a bounded-loop fix made earlier generalized correctly rather than being a Gemini-specific patch.

### What was accepted as-is vs. corrected or rejected, and why

- **Accepted as-is:** the overall project structure, the routes → controllers → services layering, and the bulk of the CRUD implementation matched the stated conventions and needed no changes.
- **Corrected:** an SQL bug in task creation (see below), raw error-message leakage to API clients, missing input validation, a missing `catch` around a frontend API call, a placeholder test file that claimed to pass without testing anything real, a guessable sequential id used as a destructive-action confirmation token (Security review, fixed to a random one), a chatbot confirm-endpoint reply that claimed success on a no-op (Review-QA), a UTC-vs-local-timezone bug in the chatbot's own "what day is today" reasoning, a second and more serious timezone bug that had silently shifted every task's due date by a day for months (see below), and fully permissive CORS with no rate limit on the paid chat endpoint (Security review's final holistic pass).
- **Rejected / deferred:** the Trello-style expansion (multi-board, drag-and-drop, auth, assignment, permissions) was deliberately not built now — tracked in `PROJECT-PLAN.md` as a "stretch tier" instead, since it's a materially larger product than the take-home brief asks for and building it now risked not finishing the actual core cleanly.

### An AI mistake, and how it was caught

The first live test of `POST /api/tasks` failed with `column "priority" is of type task_priority but expression is of type text`. The generated SQL was `COALESCE($4, 'medium')` inserting into an enum column; Postgres can't infer that a bound parameter inside `COALESCE` should be cast to the enum type, so it defaulted to `text` and the insert failed. This looked completely correct on a static read of the code — it only surfaced once the container was actually run against real Postgres and exercised with `curl`. Fixed with explicit casts (`$4::task_priority`, `$5::text[]`). This is the concrete reason the workflow leaned on actually running `docker compose up` and hitting the live API at every milestone, instead of trusting generated code by inspection alone.

A more interesting one happened later, and it was the AI's own mistake, not the code's: the chatbot once described a task — a title, time, priority, tag, and a note about emailing a confirmation — that matched none of the known seeded demo tasks. The first conclusion was that the model had hallucinated an entire fake task, a serious failure for a tool whose whole premise is trustworthy grounding via real function calls. That diagnosis was wrong, and the user corrected it immediately: they had created that exact task themselves, live, through the chatbot, in a step the assistant hadn't seen. Checking the actual database row instead of acting on the hallucination theory showed the task was completely real — and surfaced a genuine, unrelated bug: the task's `description` field had existed in the database and round-tripped through the API since the very first milestone, but had never once been shown anywhere in the frontend, because nothing had ever populated it with real content until the chatbot did. The general lesson: when a chatbot's output looks wrong, check the actual database before assuming the model is at fault — the discrepancy can be a real, pre-existing feature gap the chatbot happened to expose rather than one it caused.

The clearest example of an actual shipped mistake, though, came from the final milestone's holistic review. An earlier fix (setting the backend's timezone so the chatbot could correctly resolve "tomorrow") had an unchecked side effect: the database driver builds a date column into a local-midnight `Date` object, which the API then serializes back to UTC — silently shifting every task's due date back by one day for as long as the timezone's daylight-saving offset is non-zero, which was true at the time. It looked fine when the earlier fix was verified, because that verification only checked that "today" was computed correctly, not that every other place a due date is read had been re-checked. It surfaced only once a review pass was asked to look at the whole application together, cold, instead of at each feature in isolation — a good argument for keeping that kind of pass in the schedule even when every individual piece has already been reviewed on its own.

Essa chamada confirmou que o formato correspondia exatamente ao esperado, e reproduziu o mesmo comportamento de múltiplas chamadas de ferramentas em cadeia visto com a Gemini, confirmando que uma correção feita antes (um ciclo limitado, em vez de um desenho de chamada única) generalizava corretamente em vez de ser um remendo específico da Gemini.

### Um erro da IA, e como foi detetado

O primeiro teste real de `POST /api/tasks` falhou com `column "priority" is of type task_priority but expression is of type text`. O SQL gerado era `COALESCE($4, 'medium')` a inserir numa coluna enum; o Postgres não consegue inferir que um parâmetro vinculado dentro de `COALESCE` deve ser convertido para o tipo enum, por isso assumiu `text` por omissão e o insert falhou. Isto parecia completamente correto numa leitura estática do código — só surgiu quando o contentor foi de facto corrido contra Postgres real e testado com `curl`. Corrigido com conversões explícitas (`$4::task_priority`, `$5::text[]`). Esta é a razão concreta pela qual o processo de trabalho passou a depender de correr sempre `docker compose up` e testar a API a correr em cada fase, em vez de confiar no código gerado apenas por inspeção.

Um caso mais interessante aconteceu mais tarde, e foi um erro da própria IA, não do código: o chatbot descreveu uma tarefa — título, hora, prioridade, etiqueta, e uma nota sobre confirmar por email — que não correspondia a nenhuma das tarefas de demonstração conhecidas. A primeira conclusão foi que o modelo tinha inventado uma tarefa inteira, uma falha séria para uma ferramenta cuja premissa é precisamente a fiabilidade das chamadas reais a funções. Esse diagnóstico estava errado, e o utilizador corrigiu-o de imediato: tinha criado essa tarefa exata, ele próprio, ao vivo, através do chatbot, num passo que o assistente não tinha visto. Verificar a linha real na base de dados em vez de agir sobre a teoria da alucinação mostrou que a tarefa era completamente real — e revelou um bug genuíno e não relacionado: o campo `description` da tarefa existia na base de dados e passava pela API desde a primeira fase, mas nunca tinha sido mostrado em lado nenhum do frontend, porque nada o tinha alguma vez preenchido com conteúdo real até o chatbot o fazer. A lição geral: quando a resposta de um chatbot parece errada, verificar a base de dados real antes de assumir que o modelo é o culpado — a discrepância pode ser uma lacuna real e pré-existente que o chatbot calhou de expor, não uma que causou.

O exemplo mais claro de um erro efetivamente enviado, no entanto, veio da revisão holística da última fase. Uma correção anterior (definir o fuso horário do backend para o chatbot conseguir resolver "amanhã" corretamente) teve um efeito secundário que ninguém verificou: o driver da base de dados constrói uma coluna de data como um objeto `Date` à meia-noite local, que a API depois serializa de volta para UTC — deslocando silenciosamente a data-limite de cada tarefa um dia para trás enquanto o desvio de hora de verão do fuso horário for diferente de zero, o que era o caso na altura. Parecia estar tudo bem quando a correção anterior foi verificada, porque essa verificação só confirmou que "hoje" estava a ser calculado corretamente, não que todos os outros pontos onde uma data-limite é lida tinham sido revistos. Só surgiu quando uma revisão foi pedida a olhar para a aplicação inteira em conjunto, de forma fria, em vez de a cada funcionalidade isoladamente — um bom argumento para manter esse tipo de revisão no calendário mesmo quando cada peça individual já foi revista por si só.
